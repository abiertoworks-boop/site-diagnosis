# サイト診断エージェント(ライト診断・改善点10個)

## 目的と納品物

URL かソースから、**根拠つきで**改善点を10個出し、PDF にして納品する。
診断は「見た目の好み」ではなく「訪問者が迷わず問い合わせまで進めるか」で評価する。

## 手順(この順で実行する)

1. **事実を集める**: `python3 scripts/collect.py <URL or HTMLパス> > facts.json`
2. **画面を撮る**: `python3 scripts/shot.py <URL> out/<name> 7`
   - 撮った画像は必ず `Read` で自分の目で確認する。
   - 待機秒数を入れる理由: 演出つきサイトは、読み込み直後だと見出しが未表示で、
     「見出しがない」と誤診してしまう(実際に起きた)。
3. **複数ページを見る**: トップだけで判断しない。ナビ・フッターから、問い合わせ・会社概要・
   料金・サービスのページを `collect.py` に通す。
4. **判断する**: 下の評価基準で、項目ごとに「事実 → 解釈 → 改善案」を書く。
5. **レポート JSON を書き、PDF にする**: `python3 scripts/make_pdf.py report.json out.pdf`
6. **PDF を画像化して全ページ目視する**(文字切れ・はみ出し・画像の欠けを確認)。

## 守ること(診断の信頼性に直結する)

- **根拠のない指摘は書かない。** 各指摘に「どのページの、どの文言/数値/画像か」を必ず付ける。
- **見えないものは「未検証」と書く。** 次は公開情報から判断できない:
  売上・CV率・流入数・検索順位・広告運用・実際の問い合わせ数・競合との比較(競合 URL を
  もらっていない場合)。推測で評価しない。
- **競合差は競合 URL が渡されたときだけ診断する。** 渡されなければ「判定不能」と書く。
- **成果を約束しない。** 「売上が上がる」「CV が◯%増える」と書かない。
- **数値の基準を出すときは出典を付ける。** 出典が確認できない目安は「診断者の目安」と明記する。
- **取得環境の都合で出たエラーを、サイトの欠陥にしない。** 例: 診断環境の外部通信制限で
  CDN やフォントが読めない場合のコンソールエラーは、サイトの問題ではない。
- **装飾画像かどうか判別できない `alt` 欠落は「要確認」とする。**
- 診断対象 URL は `collect.py` の `guard_url` を通す(内部ネットワークへのアクセスを防ぐ)。

## 評価基準(10項目・各5点)

| 項目 | 5点の状態 | 見るもの(事実の取り方) |
|---|---|---|
| ファーストビュー | 画面内で「誰の・何を・どうする」が分かり、主CTAが見える | PC/スマホの FV 画像、H1、リード文 |
| 誰向けか | 対象(職種・悩み・規模)が文言で特定できる | FV〜最初の2セクションの文言 |
| 強み | 他社と置き換えられない根拠(数字・方法・実績)がある | `headings.h2`、本文、`numbers_in_text` |
| ベネフィット | 機能でなく「得られる変化」が書かれている | 見出し・本文 |
| CTA | 主CTAが1つに絞られ、文言が行動を示し、複数箇所にある | `cta.items`、FV 画像 |
| 信頼性 | 実績・声・運営者・料金・法的表記が揃う | `trust_signals`、会社概要 |
| 導線 | 不安が出る箇所の近くに次の一歩がある | ナビ、CTA の出現位置、外部リンク |
| スマホ表示 | 横スクロールなし、押しやすい、連絡手段に1タップで届く | `shot.py` の出力、`tel:` の有無 |
| SEO | title/description/見出し/OGP/構造化データが整う | `head`、`structured_data_types`、`side_files` |
| 問い合わせまでの流れ | 入力項目が妥当、返信目安・送信後の案内がある | フォーム項目数、送信後の文言 |

## 店舗を持つ個人事業主・中小企業向けの追加確認(メインのターゲット)

10項目の評価に加え、次を事実で確認し、改善点の候補にする。

| 確認項目 | 見るもの |
|---|---|
| 住所・地図・アクセス | 住所の文字表記、地図埋め込み・地図リンクの有無 |
| 営業時間・定休日 | 文言の有無、特別営業日の更新日が古くないか |
| 電話・予約のタップ導線 | `tel:` リンク、予約フォーム/外部予約サービス/LINE へのリンク |
| 店内・外観・スタッフの写真 | 実写の有無(素材画像だけでないか) |
| メニュー・料金 | 価格の明示、税込/税別の表記 |
| 口コミ・お客様の声 | 掲載の有無、掲載の許可が取れているかは確認できない |
| 更新の鮮度 | お知らせ・ブログの最終日付、著作権表記の年 |

**確認できないこと(必ず「未検証」と書く):** Google ビジネスプロフィール・地図上の表示順・口コミ件数
(サイト外の情報で、取得できた場合のみ診断する)、実際の来店数・予約数。

## 6つの問い(判定は ○ / △ / × / 判定不能)

誰向けなのか / 何が強みなのか / なぜ選ぶべきなのか / CTAが分かりやすいか /
顧客の不安を解消できているか / 競合との差が伝わっているか(競合情報がなければ判定不能)

## 改善点10個の書き方

優先度順(効果が大きく工数が小さいものを上位)。各項目は次の4点を必ず含める。

- **問題**: 訪問者が何で迷う/離れるか
- **根拠**: ページ名・実際の文言・計測値(事実のみ)
- **改善案**: そのまま実行できる具体案(文言例まで書く)
- **目安**: 効果(高/中/低)と工数(小/中/大)。診断者の判断であることを明記

## レポート JSON

```json
{
  "site_name": "", "url": "", "date": "YYYY-MM-DD", "plan": "ライト診断(改善点10個)",
  "summary": "総評(結論→最優先の3点)",
  "images": {"pc": "out/x/pc_fv.png", "sp": "out/x/sp_fv.png"},
  "scorecard": [{"item": "ファーストビュー", "score": 3, "comment": ""}],
  "six_questions": [{"q": "誰向けなのか", "verdict": "△", "answer": "", "evidence": ""}],
  "improvements": [{"rank": 1, "title": "", "issue": "", "evidence": "", "fix": "", "impact": "高", "effort": "小"}],
  "unverified": ["…"],
  "method": "取得日時・見たページ・使った方法"
}
```

## 実運用で見つかった落とし穴(必ず守る)

1. **スマホ画面は iPhone 相当の User-Agent で撮る**(`shot.py` は対応済み)。サイトが UA で
   PC版/スマホ版を出し分けると、既定の UA では PC版を縮小した画面になり、「メニューが画面を覆う」
   などの誤診が起きる(実際に起きた)。
2. **ボタンに見える要素は、実際にタップして確認する。** `elementFromPoint` でリンクか調べる。
3. **ロゴ画像だけの H1 は、img の alt を見る。** テキストが空でも H1 が無いとは限らない(`collect.py` は対応済み)。
4. **構造化データは `@graph` の中も見る**(対応済み)。「無い」と書く前に確認する。
5. **robots.txt の `Sitemap:` の行を読み、そのURLが取得できるか確認する。** `/sitemap.xml` だけで判断しない。
6. **短時間に連続取得しない。** 429(アクセス制限)が出る。ページ間は数秒空け、ログに残す。
7. **403/ENOTFOUND は「診断不能」と書く。** 回避しない。原因が環境かサイトかを切り分けて伝える
   (例: 同時に example.com で確認する)。
8. **ベンチマーク比較は、業種・意思決定者が違うなら冒頭で明記し、事実の比較に限る。**
   成果・集客力の優劣は判断しない。ベンチマーク側の課題も「取り入れない点」として書く。
9. **日付を書くときは出典を示す**(例: フィードの pubDate)。URLの日付は投稿日の目安にとどめる。
10. **福祉・医療・士業など広告規制のある業種は、表現の適否を断定しない。** 「所管の確認が必要」と書く。
11. **「押せない/見えない」と書く前に、状態を変えて再確認する。** スクロールで隠れ、上に戻すと再表示される
    ヘッダー(opacity 0 + pointer-events none)があり、下スクロール直後に調べると「メニューが押せない」と
    誤診する。上へ少し戻して再検証し、仕様か不具合かを切り分ける。
12. **同業比較では、事業規模(単独/多店舗/全国チェーン)を冒頭に書く。** 規模が違えば、サイトの役割
    (教室検索・採用など)も違う。優劣ではなく、構成・導線・情報の事実を比較する。

13. **全体画像は、スクロールで表示される要素を描画させてから撮る**(`shot.py` は対応済み)。しないと白い空白が写り、
    「コンテンツがない」と誤診する(実際に起きた)。ただし、撮影した画像は必ず目視で確認する。
14. **法人向け(B2B)サイトは、評価項目を読み替える。** 『誰向けか』=顧客の種類ごとの入口、
    『CTA』=資料請求・お問い合わせ・パートナー募集、『信頼性』=電話・メール・資本金・実績・試験や認証・
    出典。購入方法(納期・ロット・支払い・保証)の有無も確認する。
15. **コントラスト比は、画面から取った色で計算し、「推定」と書く。** 基準(WCAG の通常文字 4.5:1)は
    出典を付ける。
16. **LINE の検出は `line.me` と `lin.ee` の両方**(対応済み)。
17. **性能・効果の強い断定表現と、副業・パートナー募集は、法律上の確認が必要になる場合がある。**
    適否は断定せず、「専門家に確認」と書く。
18. **誤記を見つけたら、原文を引用して「〜の誤りと思われる」と書く**(断定しない)。
19. **動画・画像の数は、画面で数えてから書く。** HTML の要素数と画面上の数は一致しないことがある。

## 既知の限界(納品前にお客様へ伝える)

- 公開情報だけの診断で、アクセス解析・広告・売上は見ていない。
- 画面の演出は取得時点の1回分で、動画・スクロール連動の演出は静止画で評価している。
- スコアは診断者の判断で、第三者機関の基準ではない。
